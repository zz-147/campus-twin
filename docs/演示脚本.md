# 演示脚本（3 分钟版 + 5 分钟版）

> 目标：在面试/答辩现场，用最短时间证明这个项目**不是大屏 Demo**，而是
> 「真实数据采集 → 故障检测 → AI 根因分析 → 闭环处置」的运维系统。

## 一、演示前 5 分钟准备

1. Packet Tracer 打开 `D:\zdsh\campus-twin\pt\campus-final.pkt`
2. NC 设备 → Real World Access → 勾选 Access Enabled，端口 58000
3. 启动后端（窗口 1）：
   ```powershell
   cd D:\zdsh\campus-twin\backend
   D:\zdsh\campus-twin\.venv\Scripts\python.exe -m uvicorn app.main:app --port 8000
   ```
4. 启动前端（窗口 2）：
   ```powershell
   cd D:\zdsh\campus-twin\frontend
   npm run dev -- --port 5173
   ```
5. 启动 AI Agent（窗口 3，W5-6 完成后）：
   ```powershell
   cd D:\zdsh\campus-twin\agent
   D:\zdsh\campus-twin\.venv\Scripts\python.exe -m uvicorn app.api:app --port 8100
   ```
6. 浏览器打开：大屏 `http://127.0.0.1:5173/`，Agent 对话页（或 Swagger `http://127.0.0.1:8100/docs`）
7. 保险措施：提前录一段完整演示视频；准备 `DRIVER=simulator` 的纯离线演示模式

## 二、3 分钟主演示流程

| 时间 | 动作 | 讲解词 |
|---|---|---|
| 0:00–0:30 | 打开 3D 大屏 | "这是校园网络数字孪生：4 个楼栋、5 台网络设备、6 台终端。注意右上角——**数据来源 PT NC 真实采集**，不是录屏。" |
| 0:30–0:50 | 点一下 SW-JX-2960 详情 | "设备详情里的管理 IP、型号、IOS 版本都来自 Packet Tracer 9 的 Network Controller REST API，采集周期 5 秒。" |
| 0:50–1:20 | 在 PT 里 `shutdown` SW-JX Fa0/1（PC-JX1 掉线） | "我做一次真实故障注入。注意看大屏——教学楼的 PC-JX1 标记会变红。" |
| 1:20–1:50 | 等 30–60 秒，观察告警列表 | "NC 大约 30–60 秒检测到，我们的后端 5 秒内生成 critical 告警并推送到前端。**这是真实的故障检测链路**。" |
| 1:50–2:40 | 向 AI Agent 提问：<br>"教学楼 PC-JX1 掉线了，帮我排查" | "AI 会调用工具查设备、主机、拓扑、健康问题，然后给出：根因（接入交换机 Fa0/1 端口 down）、依据（引用具体 IP/时间/数据源）、排障步骤、修复命令。" |
| 2:40–3:00 | 在 PT 里 `no shutdown`，观察恢复 | "恢复后告警自动清除，形成闭环。" |

## 三、5 分钟加长版（加两个点）

3. 再做一个故障：`shutdown` 或删除核心链路 → 展示"链路断开 → 拓扑断链 → AI 定位到具体链路两端端口"
4. 展示 AI 评测报告：20 个故障场景，根因命中率 X%、设备定位命中率 Y%（引用 eval/report.json）

## 三·五、W9 新功能演示（加设备 / 删数据 / 多 Agent，约 2 分钟）

| 步骤 | 操作 | 讲解词 |
|---|---|---|
| 1 | 在 PT 里拖一台新交换机并配好（如宿舍楼 SW-SS-2961，配置可让 AI 生成） | "我先问 AI 怎么加设备——它会给我 PT 型号、端口级连线、完整 CLI 配置。" |
| 2 | 向 AI 提问："我想在宿舍楼加一台 2960 接入交换机，怎么配置？" | AI 输出接入方案 + 生成**场景 action 卡片**（待确认） |
| 3 | 在 PT 里按方案配置，等 5–10 秒 | "后端采集发现新设备，侦察 Agent 自动推断归属楼栋，场景 Agent 生成位置——大屏自动出现新设备和楼栋，无需刷新。" |
| 4 | 大屏顶部出现「发现 1 台新设备」→ 点【确认加入】 | "确认后转入正式场景；不满意可以撤销。" |
| 5 | 告警面板：删一条已恢复告警 → toast「撤销」；点「清空已恢复（N）」 | "历史故障记录可以一键清理，软删除 + 审计 + 可撤销；活跃告警只能静默不能删。" |
| 6 | 向 AI 说："把已恢复的告警清空" | AI 只生成**红色危险操作卡片**，点【取消】不执行；"Agent 不直接执行写操作，必须我确认。" |
| 7 | AI 面板「历史会话」→ 删除一条 / 清空全部 | "对话历史也能一句话删或手动删。" |

**面试讲点**：多 Agent 协作（主 Agent 编排 + 4 个专职子 Agent）、人机协同（PT 无写 API，Agent 只生成方案与待确认动作）、软删除+审计+可撤销的变更安全设计。

## 四、面试官必问 & 标准回答

| 问题 | 回答要点 |
|---|---|
| 数据是真的吗？ | PT 的 Network Controller 提供 Cisco DNA Center 风格北向 REST API；拓扑、设备、主机、健康问题、路径追踪都是仿真网络真实运行状态。只有端口流量/温湿度这类 PT 不暴露的指标由行为仿真引擎生成，且明确标注 `source=simulator`。 |
| 为什么不用 eNSP/SNMP？ | eNSP 无开放采集接口，PT 9 的 NC 原生提供 REST API，数据可复现、可版本化，更适合做"可验证"的项目。 |
| 为什么不用 SpringBoot/MySQL？ | 单人项目避免双后端过度设计；数据量级（5 设备/6 终端/5s 周期）SQLite 足够，存储层已抽象可换库。 |
| 项目最难的点？ | ①多源数据时序同步：NC 用仿真设备时钟（实测与宿主机差 10 分钟），需区分 observed_at / source_ts；②NC 告警清除滞后（>3 分钟），所以自建检测规则用 host ping/设备可达性判定恢复，不依赖 NC issue 生命周期；③告警风暴降噪。 |
| AI 是不是套壳？ | Agent 通过 function calling 调用 8 个真实数据工具；系统提示强制引用真实数据、禁止编造；有 20 场景评测集量化根因准确率；LLM 可切换（DeepSeek/OpenAI/Ollama/mock），不绑定单一模型。 |
| 如果接真实校园网？ | 数据接入层是驱动可插拔设计：netcon 驱动（当前）/ SNMP 驱动 / Netmiko 驱动 / 回放驱动，只需实现 Driver 协议；点位模板 + 设备注册表保证接入成本可控。 |

## 五、翻车预案

| 风险 | 预案 |
|---|---|
| PT 崩溃/NC 挂 | 切 `DRIVER=simulator` 演示模式（后端内置行为仿真，界面标注"仿真数据"） |
| 网络/LLM 不可用 | 切 `LLM_PROVIDER=mock`（离线规则回答），功能可用 |
| 端口被占 | 探针自动探测 NC 端口；后端/前端端口可改 |
| 现场没网 | 全部本地跑，只有真实 LLM 调用需要外网 |
