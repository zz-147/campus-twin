# 故障注入实验记录（闭环验证）

> 目的：验证「PT 仿真网络故障 → NC 检测 → 后端采集 → 告警 → 前端联动」整条链路是真实数据，
> 并为 W3 检测引擎提供实测依据。
>
> 实验日期：2026-10-29 21:43–21:55（宿主机时间）

## 一、故障注入（21:43 左右）

操作：在 SW-JX-2960 上执行

```
interface FastEthernet0/1
 shutdown
```

影响：教学楼 PC-JX1（192.168.20.10）链路断开。

## 二、观测结果

| 时间 | 观测点 | 数据 |
|---|---|---|
| 21:43:42 | NC 健康问题 | `PC-JX1 / Connectivity / "Device is down"` |
| 21:43:42 | NC 主机列表 | `PC-JX1 ping=FAILURE` |
| 21:43:42 | NC 健康度 | healthyClient `100% → 83%`（6 台中 1 台掉线） |
| 21:43:42 | 后端告警 | `id=15 [critical] 网络健康问题：Connectivity \| Device is down` |
| 21:43:42 | 后端状态 | `issues=1`，其他 5 台设备/主机不受影响 |

**链路结论**：故障发生后约 **30–60 秒**被 NC 检测，后端 **5 秒采集周期**内捕获并生成 critical 告警，
WebSocket 实时推送到前端；前端 PC-JX1 标记变红 + 脉冲，告警列表置顶。

## 三、恢复（约 21:50）

操作：`no shutdown`

| 观测点 | 数据 |
|---|---|
| NC 主机列表 | `PC-JX1 ping=SUCCESS` ✅ |
| NC 健康度 | healthyClient 回到 **100%** ✅ |
| NC 健康问题（issue 列表） | ⚠️ **超过 3 分钟仍未清除**（NC 问题生命周期有延迟） |
| 后端告警 | 未生成 `health_issue_cleared`（因为 NC issue 未消失） |

## 四、暴露出的问题（W3 待修）

1. **NC 时钟与宿主机偏差约 10 分钟**
   - 故障实际发生 21:43:42（宿主机），NC 返回的 `issueTimestamp` 是 `21:33:14`（仿真设备时钟）。
   - → 后端入库/展示需统一时间基准（记录 `observed_at` 宿主机时间，保留 `source_ts` 原始时间）。
   - → 这正是项目难点"多源数据时序同步"的**真实证据**，可写入文档/面试。

2. **NC issue 清除有延迟（>3 分钟）**
   - 恢复后 host ping 已 SUCCESS，但 NC 的 `health-issues` 仍返回该问题。
   - → W3 检测引擎不能只依赖 NC 的 issue 列表，应同时用 **host pingStatus / 设备 reachability** 做自有判定，
     实现"恢复即清除"，并可做双源交叉校验。

3. **后端 host 状态新鲜度不足**
   - 故障期间后端 `/api/hosts` 的 `ping_status` 仍为 `SUCCESS`（NC 侧为 FAILURE）。
   - → 需要检查 host 采集/更新逻辑，确保每轮采集都刷新主机状态。

4. **告警噪声**
   - 换核心期间产生的 11 条历史 issue 在恢复后集中产生 11 条 `info` 级"已清除"告警，淹没有效信息。
   - → W3 需要：告警聚合/降噪、info 级恢复通知折叠、历史告警 TTL 清理。

## 五、结论

- 真实数据链路 ✅ 验证通过（故障检测端）。
- 恢复端 NC 有延迟，需由本项目自建检测逻辑补齐（这正是"可运维、可智能诊断"的价值点）。
- 本次实验数据可直接用于 W3 检测规则的阈值/时序设计。

# 第二轮实验（2026-10-30 16:00–16:15，W3 检测引擎上线后）

## 一、故障注入

同样的操作：SW-JX-2960 `shutdown` Fa0/1（PC-JX1 掉线）。

## 二、检测结果（W3 自建规则生效）

| 观测点 | 数据 |
|---|---|
| 后端活跃告警 | **2 条 critical**：① `host_down 主机离线：PC-JX1`（detail 直接定位 `SW-JX-2960 FastEthernet0/1`）② NC 原生 `health_issue` |
| `/api/hosts` | PC-JX1 `ping_status=FAILURE`（**新鲜度修复生效，不再显示旧值**） |
| NC `/host` | PC-JX1 `ping=FAILURE` |

## 三、AI 排障（真实 DeepSeek）

提问："教学楼 PC-JX1 掉线了，帮我排查原因并给出恢复步骤"

- 端到端 **20.8 秒**、3 步、8 次工具调用
- 根因定位：**SW-JX-2960 FastEthernet0/1 接入端口侧**（非交换机/上行链路）
- 依据链：交换机 Reachable/Managed、上行 Fa0/24 利用率 33.95% 正常、同 VLAN 的 PC-JX2 ping SUCCESS → 故障隔离在 Fa0/1 单端口
- 主动指出数据不一致：设备详情 `attached_hosts=[]` 与主机清单不符（采集关联关系不全）

## 四、恢复（`no shutdown`）

| 观测点 | 结果 |
|---|---|
| 后端 `/api/hosts` | PC-JX1 ping_status=SUCCESS |
| 后端 `alerts?state=active` | **0 条**（host_down / health_issue 均已 cleared） |
| 告警 clear_reason | "pingStatus FAILURE -> SUCCESS（按数据源实际状态判定）" ← **不依赖 NC issue 生命周期** |
| `alerts/summary` | active 0 / cleared 9 |
| NC 侧 issue | 仍存在，后端标记 `stale_source=true` |

**结论**：W3 的恢复判定按预期工作，NC 滞后不再拖累告警关闭。

## 五、本轮新发现（W7.1 修复项）

前端把 `stale_source=true` 的 NC 滞后 issue 当作"活跃"渲染，导致：
- 顶部「活跃告警 0」与告警列表「PC-JX1 活跃」矛盾
- 3D 场景 PC-JX1 恢复后仍显示红色/脉冲

→ 修复：前端活跃语义只认 `/api/alerts?state=active`；stale issue 显示为「已恢复 · NC 记录滞后」，
不计数、不脉冲（task-7）。
